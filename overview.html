A working CI/CD pipeline from git push to a live container on EC2 — with test, build, ECR push, deploy, health check, and SNS notification.

Python 3.12 Flask MongoDB Atlas Docker GitHub Actions AWS ECR AWS EC2 AWS SSM Ansible Terraform Amazon SNS

What this is

Forked from mohanDevOps-arch/flask_Practice. A small Flask + MongoDB "student registration" app becomes the vehicle for a real CI/CD pipeline:

  • Every push to main that touches app / build / deploy code runs pytest, builds a Docker image tagged with the commit SHA, pushes to ECR, and deploys onto EC2.
  • The pipeline discovers the target instance ID (and ECR repo / EIP / SNS topic) from Terraform's S3-backed remote state — no per-resource GitHub secrets to maintain.
  • Deployment happens over SSM (no SSH, no port 22) using the built-in AWS-ApplyAnsiblePlaybooks document — SSM pulls this repo onto the instance and runs an Ansible playbook there. The run-scoped GITHUB_TOKEN is stashed in an SSM SecureString so the fetch authenticates.
  • Runtime secrets live in SSM Parameter Store as SecureString and are fetched on the instance, never transiting the CI runner.
  • A /health endpoint is the real deploy gate — the pipeline only reports success if it returns 200 {"status":"healthy"}.
  • Success/failure notifications go through an SNS topic with tailored subject + body.

Pipeline stages

Triggered on push to main, path-filtered to only fire on app / build / deploy code changes. Docs, Terraform, and marketing HTML are ignored — use workflow_dispatch to force a run.

CheckoutLatest source on push (paths-filtered).
Installpip install -r requirements.txt.
Testpytest against a Mongo service container. Fails the build.
TF outputsterraform init + output -raw on S3-backed state.
Builddocker build, tagged with the commit SHA.
Push ECRAuthenticated ECR push (SHA tag + latest).
DeploySSM ↦ Ansible on the instance ID from state. Idempotent.
VerifyExternal curl /health retries with hard fail.
NotifySNS publish. Failure email names the failed stage.

Getting started

  1. Fork & clone — gh repo fork mohanDevOps-arch/flask_Practice --clone.
  2. Provision AWS — 
    cd infra/terraform
cp terraform.tfvars.example terraform.tfvars   # fill mongo_uri, secret_key, notify_emails
terraform init && terraform apply
  3. Push outputs into GitHub secrets — copy the gh secret set … block from infra/terraform/README.md.
  4. Confirm the SNS email — AWS sends a one-time "Confirm subscription" link to each address in notify_emails.
  5. Push a change — the pipeline runs on main, deploys the image, and emails the outcome.
  6. Test the failure path — break a test intentionally to receive a failure email with the correct stage name.

Trade-offs called out

Static access keys, not OIDC

Simpler setup; the GHA secret access key lives in Terraform state (S3, encrypted). Rotate with terraform apply -replace=aws_iam_access_key.gha.

Single EC2, no load balancer

Matches the assignment brief. Deploy has a brief moment of downtime during docker stop → run.

Runtime secrets in Parameter Store

MONGO_URI / SECRET_KEY never touch the CI runner or CloudTrail command params. Ansible fetches them on the target via the EC2 IAM role.

S3 remote state, no DynamoDB lock

State lives in an S3 bucket outside this stack (versioned, AES256, public-access blocked). The pipeline is read-only against state — CI never runs apply. Add DynamoDB locking if multiple humans start applying concurrently.

GH token stashed in SSM SecureString

AWS-ApplyAnsiblePlaybooks' tokenInfo only accepts the {{ssm-secure:name}} form, so the run-scoped GITHUB_TOKEN is written to Parameter Store each run and referenced from there. Raises the GitHub API limit from 60/hr per-IP to 5000/hr per-token.

Path-filtered triggers

Deploys only fire when app / build / deploy files change. README / overview / Terraform edits skip CI entirely — use workflow_dispatch if you really need to force a run.
